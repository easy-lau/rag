# 问答模块修复方案（证据与状态层）

> 目标：根治近 7 天生产 Trace 中问答侧的失败源，而不是在现象上打补丁。
> 范围：证据裁决、V3 语义入口、路由与配置、回答体验。
> 边界（本方案不触碰）：ACL 与对象数据范围、产品/版本适用范围、`unverified_generation` 诚实标记、
> schema 校验的 fail-closed 语义、`rag_general_fallback_mode` 默认值。

## 1. 现状证据（2026-08-01 ~ 08-07，351 次问答）

`chat.response` 按 `evidence_status` 分布：

| status | 次数 | 占比 | 说明 |
| --- | ---: | ---: | --- |
| hit | 119 | 34% | 正常命中 |
| insufficient_evidence | 66 | 19% | 证据未闭合，无回答 |
| needs_clarification | 51 | 15% | 需要用户选择/补充 |
| partial | 38 | 11% | 带诚实标签的部分回答 |
| skipped | 34 | 10% | 未生成（语义澄清/无基线） |
| no_hit | 25 | 7% | 未召回 |
| error | 10 | 3% | 基础设施失败 |
| scope_mismatch | 6 | 2% | 显式范围不符 |
| unverified | 2 | 1% | 兼容状态 |

证据裁决（`rerank.completed`）：66 失败 / 53 成功，尝试中约 55% 失败。

`evidence.model_adjudication` 失败明细（139 次事件）：

| 失败类型 | 次数 | 根因层 |
| --- | ---: | --- |
| TimeoutError（含 `TimeoutError: `） | 47 | 超时窗口 60s 过大，供应商响应慢 |
| `This response_format type is unavailable now` | 5 | 旧链路绕过结构化输出协商层 |
| `小文档证据选择模型返回空内容` | 5 | 模型返回空正文被当作硬失败 |
| `rerank_contract_circuit_open` | 5 | 熔断生效（方向正确，需校准键与阈值） |
| `联合重排模型返回空内容` | 2 | 同空内容问题 |
| 其它（skipped/no_candidates） | 若干 | 正常降级 |

V3 语义入口（410 次 `execution_decision`）：`applied` 131、`deferred` 205、`fallback` 72（timeout 35、model_error 17、`schema_shape_invalid` 7、校验拒绝 11）、`clarification` 2。

意图路由来源（350 次）：`rule` 199、`llm` 71、`fallback` 46、`evidence_pending_rule` 27、`llm_fallback` 7；意图模型 7 天内 37 次超时、2 次 `model not found: objectId`（占位符配置，8-05 后已修正）。

核心结论：

1. 问答侧最大的失败源是**证据裁决模型不可靠**（超时 + 空内容 + 协商绕过），不是检索召回。
2. 裁决失败后被统一当作“证据未闭合”，造成大量 `insufficient` / `partial` / 假澄清。
3. V3 降级本身有兜底，但存在“语义范围澄清过度触发”和少数“V3 失败后整轮 skipped”的空洞。
4. 已修复的基线（结果引用记忆、证据两轴模型、生成门禁）不得被后续改动回退。

## 2. 修复原则（反补丁约束）

1. **先契约，后代码**：先定义裁决结果、超时、自动选档的共享契约，再改各调用点；禁止先加 per-case 特判。
2. **失败必须是契约值，不是异常**：空内容/超时/协议拒绝是“模型无结论”，与“供应商故障”是不同的状态，必须分开表达，禁止在调用点 `try/except` 吞掉再续答。
3. **单一事实来源**：裁决超时只允许一个读取点；结构化输出协商只允许一套实现；熔断只允许一套键。
4. **降级路径必须完整可运行**：V3 失败后必须落到本地计划；本地计划不可运行时是设计缺陷，不是用户可见的“重试”。
5. **每个修复带回归测试 + Trace 验证门**：没有可观测指标变化的改动不合并。

## 3. P0-1 证据裁决可靠性（契约层重构）

### 3.1 裁决结果契约：区分 inconclusive 与 failed

现状：`core/reranker.py` 的 `select_small_document_evidence_with_coverage` /
`joint_rerank_with_coverage` 遇到空内容直接 `raise ValueError("…返回空内容")`，
上层把空内容、超时、400 协议拒绝全部归一为 `model_adjudication_state=failed`，
再整体走 unverified fallback。

根因：reranker 的输出契约没有区分“模型没有给出结论”和“基础设施失败”。

方案：定义裁决结果契约（数据类，非异常）：

```python
@dataclass(frozen=True)
class AdjudicationOutcome:
    status: Literal["succeeded", "inconclusive", "failed"]
    reason: str | None = None      # inconclusive: empty_content / contract_rejected / timeout
    elapsed_ms: int = 0
    # succeeded 时才携带重排后的候选/证据选择
    payload: Any = None
```

- `succeeded`：正常进入重排后证据路径。
- `inconclusive(empty_content / contract_rejected / timeout)`：走已具备的确定性
  auto-confirm（`candidate_auto_confirmed` + `role_mode=direct`），并打
  `adjudication.inconclusive` Trace；不降级证据角色、不要求用户确认、不烧满超时。
- `failed(provider_infrastructure)`：保持现有 fail-closed（熔断、保留候选供澄清）。

不在 pipeline 里为每种错误加 `if`，所有判定收口在 reranker 契约层。

### 3.2 超时单一来源

现状：DB settings 把 `rerank_timeout_seconds` 覆盖为 **60s**（默认 15s）；
`core/rag_v2/pipeline.py:213` `_model_evidence_adjudication_timeout_seconds`
已经是唯一读取点，但旧链路 `rerank_with_status` 仍用 `llm_request_timeout_seconds`（60s）。

方案：

- DB `rerank_timeout_seconds` 改回 15s（运行时配置，属校准而非代码补丁）。
- 确认所有裁决调用（small document / joint / legacy rerank）都传入同一 deadline，
  不允许任何路径回落到全局 LLM 超时。

### 3.3 结构化输出协商收口

现状：`core/reranker.py:2125` 的 `rerank_with_status`（`api/search.py` 旧链路）
直连 `client.chat.completions.create(..., response_format={"type":"json_object"})`，
绕过 `core/structured_output.py` 的 `create_structured_completion`
（json_schema → json_object → plain 协商），且自带 60s 超时。
这是 `This response_format type is unavailable now` 400 的主要来源。

方案：把该调用改走 `create_structured_completion`，复用 `provider_identity`
能力探测与降级缓存；删除该路径上重复的 `response_format` 选择逻辑，
保证全系统只有一套协商实现。

### 3.4 熔断键校准

现状：`rerank_contract_circuit_open` 已生效（5 次），但需要核对键与阈值。

方案：

- 熔断键 = `(provider_identity, model)`，不按问题/知识库维度熔断。
- 连续失败阈值与半开恢复保持现状或收紧（≤3 次连续失败触发）。
- `inconclusive`（空内容/超时）不计入熔断失败次数——空内容是模型行为，
  不是供应商故障，熔断只对协议级/连接级失败生效。

### 3.5 P0-1 验证门

- 单测：provider 返回 `response_format unavailable` → 协商降级成功；
  空内容 → `inconclusive` → 确定性回答（`direct_evidence_count>0`、
  `covered_requirement_ids` 非空、无 `generation.skipped`）；超时 → `inconclusive` 而非 failed。
- 全量回归：`cd backend && python3 -m unittest discover -s tests`（当前基线 1208 通过）。
- 生产对比（部署后 7 天）：`rerank.completed succeeded=true` 占比、
  `insufficient_evidence` / `partial` 占比，应显著下降；无新增 `generation.skipped`。

## 4. P0-2 V3 降级与过度澄清

### 4.1 语义范围澄清过度触发

现状：`execution_baseline_not_runnable`（19 次 skipped）绝大多数携带
semantic clarification contract（如“请选择云枢版本 6”）。其中一部分场景
范围内只有一个已授权候选文档，却仍要求用户选择。

根因：scope 收集阶段只统计“互斥范围候选数”，没有先做
“已授权候选文档数=1 自动选中”。

方案：在 `core/query_analysis_execution.py` 的 baseline 收集阶段定义共享规则
`auto_select_single_authorized_scope`（与证据侧 `candidate_auto_confirmed`
同一哲学）：

- 范围内已授权候选文档数 = 1 → 自动选中，不进入语义澄清；
- ≥ 2 → 保持澄清（这是真实的多版本歧义）；
- 0 → 维持 fail-closed。

该规则只属于 gate 层，不允许在单个查询/文档上特判。

### 4.2 V3 失败后 baseline 必须可运行

现状：V3 失败多数已回退本地基线（65 次 `query.understanding.v3.fallback`），
但存在 baseline 也不可运行的少数场景导致整轮 `skipped`。

方案（先取证再改）：

- 审计 `query.understanding.v3.fallback` 中 `baseline.runnable=false` 的
  Trace（事件 `query.execution` / `execution_baseline_not_runnable` 的
  `baseline_fingerprint`、`unresolved_reason`），列出不可运行的具体原因
  （bridge 语义校验失败、scope 未决等）。
- 修复对应 baseline 编译缺口；最终约束：**知识问答请求不允许因 V3 失败而整轮
  skipped**，必须落到本地计划（legacy 等价路径），并打
  `query.understanding.v3.fallback=baseline_local` Trace。

### 4.3 schema_shape_invalid

保持 fail-closed（不信任模型输出），只允许在协商层（`create_structured_completion`）
做一次 plain-text 重试；不在业务层新增 schema 特判。

### 4.4 P0-2 验证门

- 单测：单候选 scope 不再澄清；多候选 scope 仍澄清；V3 失败后请求始终执行本地计划。
- 生产对比：`execution_baseline_not_runnable` 次数与 `skipped` 占比下降。

## 5. P1-1 no_hit / error 回答体验

现状：`no_hit`（25 次）与 `error`（10 次）只返回“未找到/稍后重试”，无引导。

方案（保持 `rag_general_fallback_mode=off`）：

- `no_hit`：结构化输出“知识库中未检索到相关内容”，附建议：检查所选知识库范围、
  更换关键词、列出相近文档标题。
- `error`：文案携带 `trace_id` 与失败阶段，便于回查 `rag_trace_events`。
- 该层只改展示契约，不改变证据/权限判定。

## 6. P1-2 settings 写入校验

现状：DB settings 曾出现 `intent_model='objectId'` 占位符（8-05 前），
`rerank_timeout_seconds=60` 也说明运行时配置缺少约束。

方案：`api/settings.py` 保存路径增加白名单校验（契约层，非逐字段 if）：

- 模型名非空且拒绝明显占位符（如 `objectId`、模板变量）；
- timeout 类字段限界 `[1, 120]`；
- 布尔字段类型校验；
- 非法值拒绝保存并返回明确错误，不允许“静默接受后运行期爆炸”。

## 7. P2 澄清 / 不足策略收敛（P0-1 生效后评估）

- 真澄清基线约 33/286 次评估（`evidence.ambiguity_assessed needs_clarification=true`）。
- P0-1 生效后先复测：若 `insufficient` / `partial` 明显下降，则剩余澄清多为真实歧义，
  再决定是否需要调整多文档澄清阈值（如相关文档数 ≥2 才追问）。
- 阈值调整必须基于评测集，不允许凭单条 Trace 拍板。

## 9. 明确不做（边界）

- 不关闭 `unverified_generation` / `partial` 诚实标记。
- 不扩大 ACL、对象数据范围或产品/版本适用范围。
- 不把 `rag_general_fallback_mode` 默认打开。
- 不把 schema 校验改为“信任模型”。
- 不硬编码业务规则、不为单个 Trace 场景加正则特判。

## 10. 已修复且不回退的基线

- 结果引用记忆：`我想看第四个` / `第四个不是《钉钉》吗` 直接按已展示列表解析
  （`core/result_reference_memory.py`）。
- 证据两轴模型：`evidence_role=direct`（答案证据）与
  `source_verification=unverified`（rerank 未校验）分离，
  `verification_basis=deterministic_candidate_scope_confirmed` 承载确定性覆盖。
- 生成门禁：接纳 direct + unverified + 确定性 basis 的来源，
  消除 `verified_source_in_unverified_generation` 导致的 `generation.skipped`。
- 语义记忆：跨轮实体复用（`普通员工→D级`）已接线（`api/chat.py` 提取、
  `active_task_state` 持久化、`conversation_context.py` 消费）。

# RAG 知识库系统架构与运行链路

> 梳理时间：2026-08-05
> 梳理范围：当前工作区代码、Docker Compose、启动脚本、数据库模型与 RAG 调试文档。
> 历史 V3 语义入口、影子任务和 anchor 预取已从在线链路移除，不再是当前架构组成部分。
> 说明：本文描述代码中的设计与执行路径，不等同于生产环境已经完成的可用性、模型服务或数据库集成验收。

## 1. 一句话概览

这是一个前后端合一部署的企业知识库问答系统：

```text
浏览器 Vue 3
    ↓ HTTP / SSE
Nginx :8001（静态前端、反向代理、上传限制、登录限流）
    ↓
FastAPI :8000（鉴权、知识库、文档、问答、检索、审计）
    ├── PostgreSQL 16 + pgvector（业务数据、分块、向量、Trace）
    ├── Chat / Embedding / Vision：OpenAI 兼容接口
    └── 文档 Worker（解析、OCR/Vision、分块、Embedding、入库）
```

问答主链路不是简单的“向量 TopK → LLM”，而是：

```text
用户请求
 → RBAC 与知识库范围校验
 → 会话上下文、意图和任务合同
 → 原问题授权检索（结构化记录 + chunk 混合召回）
 → 记录级筛选与统一证据契约
 → Evidence Bundle 闭合校验
 → 互斥范围澄清或低温度生成
 → SSE 返回、ChatTurn 和 Trace 持久化
```

## 2. 部署与进程拓扑

### 2.1 Docker Compose

当前仓库只保留一个 `docker-compose.yml`，包含三个服务：

| 服务 | 作用 | 生命周期 |
| --- | --- | --- |
| `postgres` | PostgreSQL 16、pgvector、业务数据库 | 持续运行，数据在 `pg_data` 卷 |
| `migrate` | 执行 `alembic upgrade head` | 一次性任务，成功后 `Exited (0)` |
| `app` | 前端 Nginx、FastAPI、文档 Worker | 持续运行，上传文件在 `upload_data` 卷 |

`app` 镜像中由 Supervisor 管理三个进程：

1. Uvicorn：监听容器内 `127.0.0.1:8000`。
2. 文档 Worker：执行 `python -m core.document_jobs`。
3. Nginx：监听容器内 `8001`，对外提供前端和 `/api` 代理。

宿主机默认通过 `8001` 访问应用，PostgreSQL 仅绑定宿主机 `127.0.0.1:5433`。生产环境应由宿主机 Caddy/Nginx 负责 HTTPS，再反代到 `127.0.0.1:8001`。

### 2.2 本地开发

本地开发将进程拆开：

```text
docker compose up -d postgres
      ├── uvicorn main:app --reload --port 8000
      ├── python -m core.document_jobs
      └── npm run dev（前端）
```

上传接口只创建文档和任务，不在 HTTP 请求中同步完成解析、OCR 或向量化。

## 4. 主要数据模型

核心数据库表位于 `backend/models/db_models.py`：

```text
KnowledgeBase
  └── Document
        ├── DocumentProcessingJob
        └── DocumentChunk（正文、embedding、chunk_index、metadata）

User ── Role ── RolePermission
                 └── RoleKnowledgeBase ── KnowledgeBase

Conversation ── ChatTurn ── Message

RagTraceRun ── RagTraceEvent
SystemSetting / IntentRouterConfig / IntentCategory
LoginLog / LoginThrottle / OperationLog
```

重要字段和约束：

- `Document.processing_revision`：文档处理版本。旧 Worker 不能覆盖新 revision 的结果。
- `Document.status`：通常经历 `processing → ready`，失败时为 `failed`。
- `DocumentChunk.metadata`：保存 `heading`、`section_key`、表格标识和适用约束等结构信息。
- `DocumentChunk.embedding`：固定按当前 Embedding 配置生成，保存前校验维度。
- `DocumentProcessingJob`：带状态、attempt、lease 和重试时间，支持 Worker 重启后继续领取。
- `ChatTurn`：绑定 `request_id`、状态、租约和生成/持久化结果，防止网络重试重复生成。
- `RagTraceRun/Event`：保存问答各阶段摘要、耗时、候选、证据和最终状态。

当前已经有“同文档相邻 chunk、同 section、拆分表格兄弟”的结构化索引和扩展能力，但还不是 PageIndex 那种独立的 LLM 章节树索引。

## 5. 文档入库运行链路

```text
用户上传文件 / 图片 / Markdown
        ↓
document.py 鉴权并写入 Document
        ↓ 同一事务
写入 DocumentProcessingJob（绑定当前 processing_revision）
        ↓ HTTP 请求结束
document-worker 领取 queued 任务（SELECT ... FOR UPDATE SKIP LOCKED）
        ↓
解析文件 / Vision 转 Markdown / Markdown 解析
        ↓
生成 chunk metadata
        ↓
批量调用 Embedding 接口
        ↓
租约和 revision 再校验
        ↓
删除该文档旧 chunks，写入新 chunks 与向量
        ↓
Document=ready，Job=completed
```

失败处理：

- Worker 任务有最大尝试次数、租约续期和指数退避重试。
- 文档被再次编辑后，旧任务会被标记为 `superseded`，不能覆盖新内容。
- 文件任务完成或超过最大重试次数后，清理上传目录中的临时源文件。
- 解析为空、Embedding 数量不一致、源文件越界等情况会进入失败链路。

## 6. 一次问答的完整运行链路

### 6.1 请求进入与授权

1. 前端调用 `/api/chat/send`，携带会话、知识库选择、问题和幂等标识。
2. FastAPI 解析 Bearer JWT，加载用户、角色能力和知识库范围。
3. 后端确认请求中的知识库全部属于用户可访问范围。
4. 恢复或创建 `Conversation`、`ChatTurn`，建立 `trace_id / request_id / turn_id`。
5. 加载已验证的历史上下文、pending 澄清和 active task；未解决的引用不会直接盲目检索。

### 6.2 路由和任务合同

系统先区分：

- `direct`：问候、平台帮助、已附原文的改写等，不读知识库。
- `v2`：企业制度、文档问答、根据知识库写作等，必须走证据链。
- `reject` / clarification：合同缺失、范围不明确、权限不足或无法安全执行。

当前默认语义入口为 V3：

```text
原问题与历史候选
  → 服务器生成 source-span catalog
  → V3 模型只能选择 catalog 中的 span
  → 后端校验选择并编译成任务合同
  → revision fence 校验问题、会话、KB/doc scope、路由状态
  → 通过后进入 V2；失败只回退当前轮安全基线
```

V3 不能自行创造检索词、事实、权限、产品/版本范围或证据关系。

### 6.3 V2 查询计划与任务图

`rag_v2/query_plan.py` 根据问题结构识别 fact、process、list、comparison、multi-part、multi-hop 等形状，生成：

- answer requirements：每个答案维度需要证明什么；
- bridge requirements：多跳问题中需要先确认的中间事实；
- applicability scope：产品、版本、项目、地区、角色等适用范围；
- query plan：每个检索任务的目的和覆盖关系。

`rag_v2/task_graph.py` 将计划编译成不可变 Retrieval Task DAG：

```text
anchor（原问题召回）
   ├── bridge task（映射/分类/条件）
   └── answer task（最终标准/流程/数值）
```

每个 answer/bridge task 只负责一个 requirement；bridge 可以是 `proof` 或 `augmentation`，不能靠文本位置或模型自由猜测依赖关系。

### 6.4 召回、扩展与重排

`retriever.py` 的候选通道：

1. pgvector 向量相似度；
2. PostgreSQL Full-Text Search；
3. `pg_trgm` 词面相似度。

各通道通过 RRF 按名次融合，避免直接相加不同分数尺度。召回结果带有通道、分数、排名、文档、chunk、section 和约束元数据。

在首轮候选已授权且已锚定文档后，系统可以有限扩展：

- 同一文档相邻 chunk；
- 同一 `section_key` 的 chunk；
- 拆分表格的同一 `table_id` 兄弟；
- bridge 事实对应的 answer 范围；
- 小文档的受限全文候选。

扩展受文档数、chunk 数、字符数、查询数和超时限制；扩展超时只降级，不抹掉首轮候选。

随后执行联合重排。重排结果区分 `direct`、`related`、`irrelevant` 等证据角色，但模型分数本身不能直接证明答案成立。

### 6.5 证据闭合与澄清

`rag_v2/evidence.py` 和 `rag_v2/evidence_graph.py` 将候选转成 Evidence Bundle / Evidence Graph：

- 每个进入上下文的 chunk 必须声明支持哪些 requirement；
- 多跳回答必须同时覆盖 bridge 和最终 answer；
- 适用对象与答案主体必须一致；
- 表格、备注、条件和同 section 内容不能被切块遗漏；
- 互斥产品、版本、项目同时相关时，先生成结构化澄清，不直接回答；
- 没有完整证据时返回 partial、insufficient、scope mismatch 等状态，不伪造 complete。

用户选择范围后，服务端保存并重新校验 KB/document allow-list，禁止回退到未授权的全库检索。

### 6.6 生成与交付

通过证据门控后：

1. 只把预算内的已授权 Evidence Bundle 注入 Chat 模型。
2. RAG 使用低温度生成。
3. 通过 SSE 向前端发送稳定的文本块、来源和状态。
4. 保存最终回答、来源快照、Token/耗时和 evidence status。
5. 结束 `ChatTurn`；如果网络重试，按 `request_id` 复用原执行或只补持久化。

无证据、范围待澄清、检索失败或持久化失败均有独立终态，不混成普通空回答。

## 7. 多轮会话与恢复

```text
request_id
  → reserve/reclaim ChatTurn
  → accepted
  → generating
  → generated（回答恢复账本）
  → completed（消息和来源持久化）
```

- 同一 `request_id` 的重复请求不会重新创建另一条逻辑回答。
- `accepted/generating` 租约过期后可以被同一请求安全接管。
- 浏览器断线、用户取消、模型异常、回答已生成但保存失败分别记录不同状态。
- 历史回答显示时，正文可保留，但来源正文会按当前 RBAC、文档 active/ready 状态重新加载；撤权后不再披露旧来源。
- 追问仅继承已验证且能唯一确定的上下文；主体、产品或版本不明确时要求用户补充。

## 8. 权限与安全边界

权限分为两层：

1. **能力权限**：如 `chat:use`、`kb:read`、`doc:create`、`search:use`、`settings:write`。
2. **知识库数据范围**：角色范围为 `all`、`selected` 或 `none`，selected 通过 `role_knowledge_bases` 绑定。

后端访问知识库相关 API 时同时校验能力和对象范围：

```text
JWT → 用户有效性 → RolePermission → capability
                         ↓
                   KB scope / kb_id
                         ↓
                   业务对象查询和检索过滤
```

其他安全边界：

- 模型密钥通过 `CONFIG_ENCRYPTION_KEY` 加密后存数据库，不回显给前端。
- 上传源路径必须位于受控上传目录内。
- 文档原图走鉴权路由；只有品牌图以公开静态目录提供。
- Nginx 对登录接口限流、限制上传体积，并禁用 FastAPI SSE 代理缓冲。
- Trace 生产默认不保存正文，只保留摘要、长度和哈希；Trace 有大小、事件数和保留天数上限。

## 9. 可观测性与排障入口

每次问答由一个 `trace_id` 串联：

```text
chat.request
 → intent / route
 → query.plan / query.execution
 → V3（如启用）
 → retrieval.plan / candidate / completed
 → rerank.completed
 → evidence.*
 → generation.*
 → chat.response / chat.error
```

排查“回答不准”时，应按以下顺序查看：

1. `trace_id` 对应的问题、知识库范围和版本/产品约束；
2. 路由是否正确选择 `direct` 或 `v2`；
3. query plan 是否遗漏 answer/bridge requirement；
4. 向量、FTS、trigram 哪些通道实际命中；
5. 候选是否在授权范围、是否被重排淘汰；
6. Evidence Graph 是否缺 bridge、条件、表格或文档闭合；
7. 实际注入生成模型的来源是否与前端显示候选一致；
8. 模型调用、SSE 或 ChatTurn 持久化是否失败。

后台可从“RAG Traces”查看列表、详情和导出；生产环境开启正文追踪前应确认数据合规，完成后关闭。

## 10. 当前架构的能力边界

### 已有能力

- 多格式文档入库和异步可恢复处理；
- 向量、关键词、trigram 混合召回；
- 同文档 section、邻居和表格结构扩展；
- V3 受约束语义理解、V2 任务图和桥接检索；
- 证据覆盖、适用范围、版本冲突和澄清机制；
- 用户、角色、能力权限和知识库对象范围；
- SSE、幂等 Turn、断线恢复、Trace 和操作审计；
- 前后端合一 Docker 镜像、Alembic 一次性迁移和上传卷持久化。

### 尚不应误称为已验证的部分

- 当前代码没有 PageIndex 那种独立的“LLM 生成章节树 + Agent 树搜索”模块；现有结构能力来自 chunk metadata、section key、邻居和表格扩展。
- 本地单元测试不能证明生产 PostgreSQL/pgvector、外部 Chat/Embedding/Vision 服务、真实权限数据和浏览器 SSE 全链路已经验收。
- RAG 效果仍取决于原始文档解析质量、分块结构、Embedding 模型、重排模型和知识库标注质量。
- `docker-compose.yml` 默认拉取远程发布镜像；本地源码修改不会自动反映到运行中的 `app` 容器，除非重新构建或使用本地开发启动方式。

## 11. 与 PageIndex 思路的对应关系

| PageIndex 思路 | 当前工程对应能力 | 差距/可借鉴点 |
| --- | --- | --- |
| 文档章节树 | `heading`、`section_key`、`section_path`、结构邻居 | 可增加按 document revision 版本化的章节树索引 |
| 先定位章节，再读原文 | 首轮 chunk 召回后扩展 section/邻居 | 可增加受约束的章节节点选择，不让模型直接扩大范围 |
| 不依赖向量 | 当前是 vector + FTS + trigram | PageIndex 更适合作为长文档内二次导航，不替换全库召回 |
| 页码/节点可追溯 | chunk、文档、section、表格元数据和 Trace | 可补充稳定页码/标题锚点引用 |
| Agent 工具调用 | V3 只能选择服务器签发 span，V2 后端编译任务 | 应保持后端权限、证据和预算边界，避免自由 Agent 绕过校验 |

推荐的演进顺序是：先建立文档结构树和节点到 chunk 的映射，再把它作为 V2 的结构检索通道，最后才评估是否需要有限的模型导航；普通问题继续使用当前混合召回。
